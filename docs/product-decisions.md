# 제품 결정과 다음 구현 기준

기준: 2026-09-07, 최초 가이드 이후 사용자의 D1~D8 답변과 후속 확인. **사용자가 확정한 방향과 아래 구현 제안은 구분한다.** 현재 구현·검증 결과는 [architecture.md](architecture.md), [development.md](development.md)를 따른다. 이 문서는 AI 요약, SQLite 오프라인, 새 점수 및 서버 연결이 완료되었다는 뜻이 아니다.

## 1. 확정된 방향

| 항목 | 사용자 결정 | 아직 정하지 않은 내용 |

## 2. 재사용과 재작성의 경계 — 제안

React/Electron 화면 틀과 Python 키보드 매핑·손가락 매칭은 재사용한다. 카메라 생명주기, 캘리브레이션·측정 상태 전환, 데이터 전달·저장 연결은 책임을 분리해 부분 재작성한다. 코드가 섞여 있다는 이유만으로 프레임워크와 인식 모델을 동시에 교체하지 않는다.

재작성의 목표는 화면·추론·판정·저장 경계를 명확하게 만드는 것이다. 속도 향상은 아직 검증하지 않았다. 변경 전후 동일 영상·PC에서 추론 지연, CPU/메모리, 누락률을 비교한 뒤 성능 개선 여부를 판단한다.

첫 통합은 상체 한 모드의 `기준 수집 → 유효 측정 → 종료 → 서버 저장 → 조회`로 제한하는 안을 권한다. 손캠은 같은 세션 계약을 사용하되 키보드 맵과 손가락 판정은 별도 모듈로 둔다. 개발 환경 버전·명령은 [dependencies.md](dependencies.md), [development.md](development.md)를 단일 기준으로 삼는다.

## 3. 매번 캘리브레이션하는 방법 — 채택 방향의 구체화 제안

1. 시작 안내에서 머리·양어깨 가시성과 화면 중앙 배치를 확인한다.
2. 한 장이 아니라 안정적으로 관측된 짧은 구간을 수집한다. 유효 표본의 중앙값을 개인 기준으로 삼고, 움직임·가림·카메라 변경 시 수집을 다시 시작한다.
3. 기준에는 모드, 카메라/스트림 식별, 해상도, 측정 정의 버전, 표본 수와 품질을 함께 기록한다. 수집 시간·허용 흔들림은 촬영 실험으로 조정할 값이다.
4. 실행 중 카메라가 바뀌거나 위치·거리 변화로 기준이 맞지 않으면 재측정을 안내한다. 추적 유실 시간은 점수에서 제외한다.

이 방식은 사용자·책상·카메라 배치 차이를 줄이지만, 사용자가 취한 자세의 건강상 적절함까지 증명하지는 않는다. 화면 문구는 “기준 자세를 수집했습니다”로 표현한다. 이전 기준 자동 재사용은 같은 구도가 확인되는 후속 기능으로 미룬다.

정면 웹캠에서 우선 관측할 것은 어깨 폭으로 정규화한 코 위치, 어깨 높이 차이와 **개인 기준 대비 변화**다. 이를 임상적인 거북목 각도나 질환 위험도로 단정하지 않는다. 최종 자세 점수는 관측값의 의미와 촬영 재현성을 확인한 후 별도 정책으로 정하고, `scorePolicyVersion`을 저장한다.

## 4. 작업 습관은 어떻게 측정하고 계산할까 — 제안

자세 점수는 “관측된 자세가 기준에서 얼마나 달라졌나”, 습관 지표는 “얼마나 계속 관찰됐고, 자세를 바꾸거나 휴식을 기록했나”를 보여준다. 자세 변화가 많다는 이유로 자세 점수를 올리거나, 오래 같은 자세라는 이유만으로 나쁜 자세로 판정하지 않는다.

공통 시간 정의: `T_run`은 사용자가 측정을 실행한 시간(명시적 중지 제외), `T_valid`는 신뢰도·가시성 조건을 통과한 관측 구간의 합이다. 프레임 간 시간 차이로 적분하되 허용 간격을 넘는 구간을 관측했다고 늘려 계산하지 않는다. `T_unknown = T_run - T_valid`로 두고, 분모가 0이면 `null/자료 없음`을 반환한다.

| 표시할 지표 | 입력·계산 | 해석과 한계 |
| --- | --- | --- |
| 관측률 | `100 × T_valid / T_run` | 모든 자세·습관 결과에 같이 표시. 카메라 가림을 숨기지 않음 |
| 연속 관찰 시간 | 유효 관측이 이어진 구간 길이; 현재 값과 최장값 | 추적 유실에서 구간을 끊음. PC 전체 작업시간이나 실제 착석시간과 같지 않음 |
| 같은 자세 유지 구간 | 정규화 특징이 이전 안정 자세 주변 허용 범위에 머문 시간 | 기준은 매 프레임이 아니라 안정 구간에 고정. 누락 시 종료되므로 실제 지속시간의 하한일 수 있음 |
| 자세 변화 빈도 | `유효 전환 횟수 / (T_valid / 3600)` | 새 자세로 이동한 뒤 일정 시간 유지될 때 1회. 복귀에도 같은 조건 적용. 잠깐 흔들림은 제외 |
| 기록된 휴식 | 사용자가 휴식 시작·복귀를 누른 구간의 수·총시간 | 자기보고 기록. 화면에서 사라짐·입력 없음만으로 휴식을 확정하지 않음 |
| 휴식 알림 대응률 | 응답 구간 관측이 끝난 알림만 대상으로 `구간 안에 휴식을 시작한 알림 수 / 대상 알림 수 × 100` | 관찰 도중 종료된 알림은 미확정으로 별도 표시. 각 휴식은 최대 한 알림에 대응 |

예: 실행 60분 중 유효 관측 42분, 자세 전환 7회라면 관측률은 70%, 변화 빈도는 유효 관찰 1시간당 10회다. 이는 계산 예시이며 목표 횟수나 건강 기준이 아니다. 관측률이 낮으면 과거보다 개선됐다는 결론을 제한한다.

자세 변화 감지에는 시작/복귀 임계값을 다르게 두는 히스테리시스와 최소 유지시간을 사용한다. 수치는 촬영 실험으로 정하고 `habitPolicyVersion`으로 관리한다. 휴식 주기 역시 제품 설정이며, 검증되지 않은 숫자를 의학적 권장값으로 표기하지 않는다.

초기에는 이 지표들을 별도로 보여준다. 하나의 “습관 점수”로 합치는 가중치는 만들지 않는다. OS 유휴시간을 추가하더라도 “입력 없음”이라는 보조 신호로만 쓰고 휴식 여부와 구분한다.

## 5. 키보드의 “어느 키가 얼마나 틀렸나” — 제안

키 `k`마다 권장 손가락 집합 `R(k)`를 정의한다. 실제 관측 손가락이 `R(k)`에 없으면 불일치, 있으면 일치다. 허용 손가락이 여러 개인 키도 표현할 수 있어야 한다. 키보드 배열과 권장 매핑은 `fingerPolicyVersion`으로 식별한다.

| 저장 대상 | 내용 |
| --- | --- |
| 분석 결과 | 세션/이벤트 식별, 키 코드, 관측 손가락, 일치·불일치·판정불가, 신뢰도, 매핑 버전 |
| 키별 통계 | 입력 수, 판정 가능 수, 일치 수, 불일치 수, 판정불가 수, 불일치 손가락별 횟수 |
| 산식 | `키별 불일치율 = 불일치 수 / 판정 가능 수 × 100`; `키별 판정률 = 판정 가능 수 / 입력 수 × 100` |

손 가림·키보드 맵 실패·시간 매칭 실패·권장 매핑 미정은 판정불가로 남긴다. 낮은 판정률 때문에 불일치율이 낮아 보이는 경우를 구분한다. 예를 들어 입력 100회 중 80회 판정, 불일치 20회면 불일치율 25%, 판정률 80%다.

문장의 맞춤법·의도한 단어·백스페이스 횟수로 오타를 추정하는 기능은 이 요구에 포함되지 않는다. 실제 키 이벤트 저장 범위(연습창만/전역)와 보존기간은 별도 결정이 필요하다. 키 순서만으로도 입력 내용을 복원할 수 있으므로 범위 확정 전 전역 입력 수집을 제품 기본값으로 켜지 않는다.

## 6. AI 요약 — 사용자 키 방식과 대안 제안

요약의 입력은 기간·모드, 점수 정책, 관측률, 자세 변화·휴식 지표, 키별 불일치 집계다. AI가 원시 영상이나 키 입력 문자열을 받아 점수를 산정하도록 만들지 않는다. 계산은 프로그램이 수행하고 AI는 확인된 수치를 설명한다.

| 방식 | 권장 역할 | 비용·구현 고려 |
| --- | --- | --- |
| 규칙 기반 문장 템플릿 | 기본 요약 및 AI 미설정·실패 시 대체 | 모델/API 없이 같은 입력에 같은 결과. 예: 관측률·최다 불일치 키를 문장으로 표시 |
| 사용자 API 키(BYOK) | 사용자가 선택한 클라우드 모델로 문장 요약 | 제공자 사용료·네트워크 필요. 제공자/모델과 전송할 집계를 화면에 표시 |
| 로컬 Ollama | 원하는 사용자에게 선택형 로컬 요약 | 별도 런타임·모델 다운로드와 RAM/VRAM 필요. 기기별 속도·한국어 요약 품질 검증 후 모델 선정 |

BYOK 호출은 Electron main이 담당하고, 화면에는 `키 등록/삭제`, `요약 생성`처럼 좁은 IPC 명령만 노출하는 안을 권한다. 사용자가 키를 입력하면 main으로 넘겨 저장하고, 일반 화면 상태에는 저장 여부만 반환한다. 키를 프론트 환경변수·localStorage·로그·Moti 서버에 저장하지 않는다.

main은 키를 OS 암호화로 보관하고 선택한 제공자에 직접 HTTPS 요청한다. Windows의 Electron `safeStorage`는 DPAPI를 사용한다. 같은 Windows 사용자 권한으로 실행된 다른 앱까지 막아주는 보호는 아니므로 “추출 불가능한 키”라고 안내하지 않는다. 채택한 Electron 버전에서 제공되는 API를 확인한다. [Electron safeStorage 공식 문서](https://www.electronjs.org/docs/latest/api/safe-storage)

Ollama는 로컬 모델과 클라우드 모델을 구분해야 한다. 로컬 옵션에서는 loopback 서비스와 로컬 모델만 사용하고 필요하면 `OLLAMA_NO_CLOUD=1`로 클라우드 기능을 끈다. 로컬 실행 시 프롬프트가 Ollama에 전송되지 않는다는 설명과 네트워크 기본값은 공식 FAQ 기준이다. 런타임·모델 배포를 기본 설치에 추가하는 결정은 별도다. [Ollama FAQ](https://docs.ollama.com/faq)

저장할 요약에는 입력 집계의 식별/기간, 데이터·점수 정책 버전, 제공자·모델, 생성 시각을 붙인다. 자료가 부족하면 그 사실을 표시하며, 생성 실패가 측정·저장을 막지 않게 한다. 현재 이 문서로 제공자 선택, API 연결, 키 보관 또는 로컬 AI 실행이 구현되지는 않는다.

## 7. 서버 저장과 미래 SQLite — 제안

현재 제품 방향은 **서버를 최종 기록의 기준으로 두는 것**이다. 서버 DB는 아직 미정이며, SQLite 오프라인 계획이 서버 DB 선택을 자동으로 확정하지 않는다. 실제 대상 DB와 보존할 데이터 확인 전 기존 초기화 SQL을 실행하지 않는다.

향후 PC의 SQLite는 조회 캐시와 미전송 기록을 맡기는 안을 권한다. SQLite 공식 문서도 장치 내 저장과 서버 데이터 캐시를 적합한 용도로 설명한다. 동기화 규칙은 Moti가 별도로 구현해야 한다. [SQLite 사용 지침](https://www.sqlite.org/whentouse.html)

1. 클라이언트에서 세션·이벤트 ID를 생성하고, 결과와 전송 대기 목록(outbox)을 같은 로컬 트랜잭션에 저장한다.
2. 서버는 사용자와 이벤트 ID를 검증하고 중복 요청을 한 번만 반영한다. 종료 재전송으로 점수·통계가 이중 집계되지 않아야 한다.
3. 서버 저장 확인 뒤 전송 완료로 표시한다. 재시작·연결 복구 시 미전송 항목을 재시도하며 `대기/완료/실패`를 구분한다.
4. 계정 전환·로그아웃·기록 삭제, 서로 다른 기기의 수정 충돌과 로컬 DB 마이그레이션 규칙을 정한다.

이는 DB 드라이버만 바꾸는 작업이 아니다. 지금은 서버 요청에 재시도 식별과 정책 버전을 준비하고, 실제 오프라인 요구가 확정될 때 SQLite·동기화를 구현한다.

## 8. UI 구성과 다음 작업 기준

공통 색상은 [tokens.css](../front/src/styles/tokens.css), 화면 틀은 [AppLayout.tsx](../front/src/components/layout/AppLayout.tsx), 버튼·대화상자는 기존 공통 컴포넌트로 모은다. 페이지를 수정할 때 의미별 색상과 공통 컴포넌트를 사용하고 페이지별 복제 버튼·임의 색상을 늘리지 않는다.

아이콘은 이미 사용하는 Lucide를 기준으로 통일한다. React 컴포넌트가 inline SVG를 렌더링하고 사용한 아이콘만 번들에 포함된다. [Lucide React 공식 문서](https://lucide.dev/guide/react)

복잡한 대화상자·선택 UI의 포커스와 키보드 접근성에는 Radix를 단계적으로 도입할 수 있다. 지금 전면 추가한 것은 아니다. [Radix 공식 소개](https://www.radix-ui.com/primitives/docs/overview/introduction). shadcn/ui는 컴포넌트 소스를 받아 직접 유지보수하는 방식이므로 필요한 부분을 검토해 채택한다. [shadcn/ui 공식 소개](https://ui.shadcn.com/docs)

이미지·일러스트는 촬영 구도 안내처럼 사용자의 행동을 설명할 때 추가하고, 출처·라이선스·대체 텍스트를 자산과 함께 관리한다. 화면 구조의 일관성은 이미지 추가만으로 해결되지 않는다.

다음 구현은 측정 불가·기준 수집·실행·중지·저장 대기/실패 상태와 데이터 계약부터 연결한다. 완료 조건은 같은 계정으로 재실행 후 기록 조회, 누락 구간 제외, 중복 종료 방지, 카메라 변경 후 재측정이다. 점수 수치·휴식 임계값·서버 DB·AI 제공자는 이 문서의 제안을 승인된 값으로 간주하지 않는다.
