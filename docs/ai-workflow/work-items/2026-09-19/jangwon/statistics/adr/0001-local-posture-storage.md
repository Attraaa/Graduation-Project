# ADR-0001: 로컬 자세 기록의 SQLite 저장과 서버 연결 경계

## 한 문장 결정

목·어깨 실측 기록을 재실행 후에도 조회하기 위해 루트 `database/`의 공통 코드와 Electron이 소유하는 SQLite를 사용하고, 버전 있는 데이터 계약으로 향후 서버 연결 경계를 남긴다.

## 배경과 문제

- 현재 상황: 통계/이력은 예시, 관측 결과는 메모리에만 존재.
- 해결할 문제: 영속 저장, 중복 방지, 계정/모드별 조회, 잠금·손상·중단 대응.
- 지금 결정해야 하는 이유: 저장 단위·재시도·시간대·소유권은 장기 데이터 호환성에 영향.
- 결정하지 않을 경우: DB와 화면이 결합되거나 서버에 의미가 다른 통계를 전달할 위험.

## 목표와 비목표

- 목표: 실제 로컬 기록과 검증 가능한 통계, 학습 동작 유지, 모드별 협업.
- 비목표: 원격 서버/동기화, 진짜 인증 교체, AI/의료 판정, 키보드/안구 저장, 기존 DB 삭제.

## 제약과 불변 조건

- 사용자는 전체 계획을 승인하고 DB 코드 위치를 저장소 루트 `database/`로 지정했다.
- `database/`는 코드 위치이며 실제 파일은 `<Electron userData>/database/posture.sqlite`에 둔다. 설치/소스 디렉터리에 사용자 기록을 쓰지 않는다.
- 기존 MySQL/SQL 자료/데모 계정은 자동 이관하거나 삭제하지 않는다.
- 기존 순수 캘리브레이션·점수·습관 정책, 카메라 동작, 0점/null 구분을 유지한다.

## 고려한 대안

### 대안 A: Electron + 내장 node:sqlite (권장)

- 설명: 루트 DB 모듈을 Electron main에서 호출하고 제한된 preload API로 접근.
- 장점: 추가 SQLite 드라이버 없이 현재 런타임 사용, UI와 저장 책임 분리.
- 단점: DatabaseSync는 동기 API이므로 큰 작업은 main을 지연시킬 수 있음. 짧은 배치/제한 조회 필요. 실제 main/패키징 검증은 남음.
- 구현 비용: schema/repository/IPC/기록 연결과 테스트.
- 운영 비용: 로컬 파일/백업 공간. 원격 서비스 비용 없음.
- 롤백 가능성: 코드 연결 제거 후 DB 원본 보존, 자동 schema downgrade 없음.

### 대안 B: 별도 드라이버 또는 Python 저장 서비스

- 설명: 외부 native/WASM SQLite 드라이버나 별도 프로세스 사용.
- 장점: API/프로세스 격리 선택 가능.
- 단점: 추가 의존성·Electron ABI/번들 또는 IPC·프로세스 생명주기 관리.
- 구현 비용: A보다 추가 배포·검증 범위가 큼.
- 운영 비용: 패키지/프로세스 업데이트 관리.
- 롤백 가능성: repository 경계에서 교체하되 schema 호환 검증 필요.

### 대안 C: 현 상태 유지

- 예상 결과: 실측 저장 없이 예시 화면 유지.
- 장점: 새 DB 계약 부담 없음.
- 단점: 사용자 목표 미달.
- 선택하지 않을 경우의 비용: 새 저장과 검증 구현.

## 최종 결정

**대안 A 승인 — 서장원, 2026-09-19.** 다음 계약을 적용한다.

1. 루트 `database/`에 DTO/검증·SQLite·migration·순수 집계를 분리한다. 모드 정책과 renderer adapter는 문서화한 담당 경로에 둔다. front 타입 검사·린트·테스트·번들에 루트 코드를 포함한다. 별도 package manager는 만들지 않는다.
2. 추가 production dependency 없이 `node:sqlite`로 시작한다. Electron 배포 런타임에서 실패하면 다른 드라이버로 임의 교체하지 않고 ADR을 재검토한다.
3. Electron이 DB와 쓰기를 소유한다. 단일 앱 인스턴스, 짧은 직렬 트랜잭션, foreign keys, 고유키, busy timeout을 사용한다. WAL을 사용하되 충돌이 완전히 사라진다고 가정하지 않는다. 백업은 SQLite backup API 또는 연결 종료 후 일관된 상태에서 수행한다.
4. 현재 데모 계정별 기록을 분리하고 시작 시 owner를 고정한다. 미로그인 측정은 유지하되 저장 불가 안내. 비동기 조회/저장을 계정 전환과 격리한다. 이는 진짜 인증 보안 경계가 아니다.
5. 세션/기준 구간 ID와 batch 순번을 사용한다. 같은 요청은 한 번 반영하고 동일 키에 다른 내용은 거절한다. 요약/시간 버킷은 같은 트랜잭션으로 저장한다.
6. 제한된 배치로 저장하고 중지·재수집·장치 변경·이동 시 구간을 확정한다. 재실행 시 미종료 기록은 중단 상태로 복구하며, 마지막 미커밋 구간의 복원은 보장하지 않는다.
7. 점수 적분합·유효/실행시간·정책 버전·캡처 날짜/시간대 근거를 보존한다. 일/시간 집계는 실제 구간 분할로 총량을 보존하고 누락 시간에는 점수를 보간하지 않는다. 이력 목록은 시작일 귀속, 상세는 날짜+시간 표시.
8. 다른 모드/점수 버전을 섞지 않고 전일 유사도 차이에 관측률을 병기한다. 기준 이탈을 의료 경고로 해석하지 않고 AI/의학은 예시 표시를 유지한다.
9. 기존 삭제 확인 UI는 현재 로컬 계정만 삭제하고 진행 중인 기록 세대를 무효화하여 지연 쓰기가 삭제 기록을 복원하지 않게 한다. 실제 사용자 데이터로 삭제 테스트하지 않는다.
10. 미래 서버 계약은 버전·안정 ID·시간·모드·수치를 담는다. 원격 인증/계정 매핑·전송/ack·outbox·동기화 충돌은 후속이다. 기존 Express API에 바로 연결하면 작동한다는 보장은 하지 않는다.

## 결정 근거

1. 현재 설치 런타임의 내장 SQLite 기본 지원을 확인했다.
2. 사용자 지정 루트 코드 관리와 UI/저장/집계 책임 분리가 가능하다.
3. ID·버전·원자 저장은 로컬 재시도와 미래 서버 계약의 근거가 된다.

## 감수하는 단점과 결과

- 강제 종료 직전의 미커밋 구간 유실 가능.
- 동일 Windows 사용자 권한의 다른 프로그램까지 DB 접근을 차단하지 않음.
- 긴 동기 작업이 main을 지연시키면 작업량 제한을 검증하고 worker 분리를 재검토.
- 서버 개통 후 별도 계정/인증/수신 계약 작업 필요.

## 영향 받는 계약

- API: 기존 HTTP 유지, 새 제한된 motiRecords IPC.
- DB/데이터: 로컬 버전 schema, owner/session/segment/batch 식별 및 시간 버킷.
- 이벤트/메시지: renderer의 SQL/경로 전달 금지, 허용 sender/프레임·값·크기·모드 검증.
- 설정: front 빌드/검사에 root 모듈 포함, 기존 잠금 사용.
- 외부 시스템: 이번 변경 없음.

## 보안·권한·개인정보

- 영상/원시 랜드마크/비밀번호/API key를 DB·로그·DTO에 넣지 않는다.
- IPC는 임의 파일/SQL 접근을 제공하지 않는다.
- 손상/미지원 미래 schema는 원본 보존과 명시적 오류로 처리한다.
- 사용자 확인 없는 실제 삭제·원격 전송·자동 보존기간 삭제 없음.

## 구현 및 마이그레이션

1. 승인 후 단계 1 계약/테스트부터 진행.
2. 새 DB 및 비파괴 migration, 기존 파일 원본 보존/백업과 무결성 검사.
3. 계획 2~7 구현·검증, root 모듈 번들 포함 확인.

## 검증

- 단위 테스트: DTO·모드/계정·null/0·시간 경계·집계·재시도.
- 계약 테스트: IPC·소유자·순번·버전·충돌·삭제 후 지연 쓰기.
- 통합/E2E: 임시 파일 SQLite rollback/재열기/무결성/동시성, Electron 측정→저장→조회→재실행과 설치 번들.
- 운영 지표: 저장 성공/실패/중단 상태, schema 버전; 비밀값 로그 금지.
- 사전 관찰: 프로젝트 Node 24.20.0 / SQLite 3.53.4. Electron 41.10.7 RUN_AS_NODE에서 Node 24.18.0 / SQLite 3.53.1. `:memory:` DB 개방 및 `SELECT sqlite_version()`만 실행, 사용자 DB 파일 생성 없음.
- 미검증: 실제 Electron main, 파일 DB/트랜잭션/백업/손상/잠금, 설치 패키지. 기존 72개 테스트는 새 DB 검증이 아님.

## 배포와 롤백

- 배포 순서: 로컬 구현/검증→Electron 빌드/패키지→별도 배포 승인.
- 호환 기간: 이전 앱은 새 SQLite 조회 미지원, 미래 schema에 오래된 코드로 쓰기 금지.
- 롤백 조건: 저장 중복/손실·계정 혼합·무결성·응답 지연 실패.
- 코드 롤백: 기록 경계 분리, 기존 측정 유지.
- 데이터 롤백: 원본/백업 보존 후 검증된 복구, 자동 삭제/down migration 없음.
- 되돌릴 수 없는 부분: 사용자가 확인 후 삭제한 기록은 코드 rollback으로 복원 불가.
