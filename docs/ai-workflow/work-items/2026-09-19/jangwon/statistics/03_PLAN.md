# 03. 구현 계획서

## 문서 정보

- 작업 이름: SQLite 실제 자세 통계와 학습이력
- 작성일: 2026-09-19
- 계획 상태: 승인 조건 반영 완료; ADR 승인 전 구현 보류
- 관련 이슈: 없음
- 관련 ADR: 필요. 계획 승인 뒤 `adr/0001-local-posture-storage.md`를 Proposed로 작성하고 별도 승인한다.
- 조사 기준: `score`, HEAD `08207145474724baf32f5df2010e36652dfea858`.

## 1. 한 문장 목표

목·어깨의 실제 기준 자세 유사도와 관찰 지표를 로컬 SQLite에 보존하여 재실행 후 통계와 학습이력을 조회하고, 향후 서버 연결에 재사용할 데이터 계약을 마련한다.

## 2. 현재 문제

통계는 고정 숫자와 그래프이고 학습이력은 예시 배열이다. 실제 측정 결과는 화면 상태에만 존재한다. 사용자 입력은 SQLite 사용을 명시했으므로 기존 제품 문서의 ‘SQLite 추후 검토’보다 이번 작업에서 우선한다. 다만 저장 주체·수명·서버 전송 계약은 세부 설계는 Proposed ADR에 작성했고 승인을 기다린다.

‘학습 모드를 수정하지 않는다’를 파일 무변경으로 해석하면 현재 측정 결과를 저장 경계로 전달할 방법이 없다. **측정 동작과 산식은 유지하고 최소 연결부만 수정하는 안**을 전체 계획 승인 범위로 적용한다.

## 3. 현재 동작

### 주요 진입점

- 파일: `front/src/pages/Statistics.tsx`, `LearningHistory.tsx`, `features/posture/PostureSession.tsx`, `components/PostureMonitor.tsx`.
- 심볼: `Statistics`, `LearningHistory`, `PostureSession`, `PostureMonitor`, `advanceEvaluation`, `getCurrentUser`, `clearStatistics`.
- 호출 주체: React 라우트와 학습 화면의 시작/중지/기준 다시 잡기.

### 현재 실행 흐름

```text
1. LearningSession이 목/어깨 모드를 선택
→ 2. PostureSession과 useSessionControls가 실행 상태와 타이머를 소유
→ 3. PostureMonitor가 카메라·기준 수집·관측·순수 점수 집계를 수행
→ 4. 약 200ms마다 MonitorSnapshot을 화면에 전달하고 중지 시 마지막 계산을 반영
→ 5. 통계/학습이력은 이 결과와 연결되지 않고 별도 예시 데이터를 표시
```

### 현재 데이터와 부작용

- 읽는 데이터: 웹캠 관측, 모드별 점수 정책, localStorage 데모 계정, 하드코딩 통계/학습이력.
- 쓰는 데이터: 측정은 React/ref 메모리만 사용. 계정·설정은 localStorage.
- 외부 API: 이 통계 경로에는 없음. Express/MySQL은 독립 구현이며 새 자세 결과를 받지 않는다.
- 이벤트/메시지: preload에 범용 `ipcRenderer`와 키보드 전용 `motiKeyboard`가 있다. DB용 계약은 없다.
- 파일/캐시: 조사한 통계 경로에 SQLite 연결 없음. 기존 SQL은 새 데이터 계약과 호환하지 않으며 실행하지 않는다.
- 설정의 `clearStatistics()`는 `postureAI.history` 키만 제거한다. 실제 학습이력은 이 키를 읽지 않는다.
- 학습이력 초기 날짜는 `2026-05-14`; 일/주/월 이동, 날짜별 목록, 상세 그래프와 되돌아가기 UI가 있다.
- `MonitorSnapshot.evaluation`에는 평균·유효시간·최장 연속 관찰·기준 이탈 횟수/시간·정책 버전이 있다. 타입에 캡처 시각과 점수 적분합은 노출되지 않는다. 화면 콜백을 샘플링해 시간대별 평균을 재계산하면 누락/경계 오류가 생길 수 있다.

## 4. 원하는 동작

아래는 전체 계획 승인에 따른 구현 기준이며 아직 구현된 사실이 아니다.

| 상황 | 현재 | 변경 후 |
|---|---|---|
| 정상 경로 | 실제 결과가 화면 메모리에만 남음 | 측정 구간을 SQLite에 기록하고 통계/이력에서 재조회 |
| 주요 실패 | 저장 경로 없음 | 저장 실패를 표시하고 같은 기록 ID로 재시도; 측정과 카메라 해제는 유지 |
| 중복/재시도 | 저장 없음 | 동일 ID/순번 재전송은 한 번만 반영, 충돌 payload는 거부 |
| 권한 없음 | 라우트 보호 없는 데모 인증 | 측정은 유지하되 계정 없는 저장/조회는 안내; 기존 계정과 혼합하지 않음 |
| 관측 없음 | 통계에 예시 점수 표시 | 점수는 자료 없음, 실제 0점은 0점; 관측 불가 시간을 휴식으로 해석하지 않음 |
| 재시작/비정상 종료 | 진행 기록 소실 | 커밋된 구간은 복원, 미종료 기록은 중단됨으로 표시; 미전송 메모리 구간은 복원 보장 안 함 |
| 키보드/안구 | 예시 이력에도 등장 | 실제 저장/집계 대상은 목·어깨만; 측정 화면은 기존 동작 유지 |

## 5. 범위

### 포함

- Electron 소유의 로컬 SQLite, 버전 있는 비파괴 스키마와 좁은 저장/조회 IPC.
- 별도 DB 디렉터리와 모드별 기록 어댑터. 공통 트랜잭션·조회 코드만 공유.
- 목·어깨 실행 구간 기록, 저장 실패/재시도, 재실행 후 학습이력 조회.
- 통계: 모드별 평균 유사도, 전일 대비 점수 차이, 시간대 추세, 실행/유효/미관측 시간, 관측률, 기록 수, 최장 연속 관찰, 지속된 기준 이탈 횟수/시간/비율.
- 학습이력의 기존 캘린더·목록·상세 흐름 유지. 초기 날짜는 실제 오늘로 변경.
- 실제 데이터 영역의 예시 값 제거. AI·의학 영역은 기존 내용을 예시로 열람하되 ‘예시·실측 연동 안 됨’ 표시.
- 기존 통계 삭제 버튼의 SQLite 연결 여부를 승인받아 처리.
- 버전 있는 직렬화 데이터와 서버 어댑터 경계, 향후 전송에 필요한 안정 ID. 서버 동기화의 미구현 범위를 문서화.

### 비범위

- 점수 공식, 기준 수집 정책, 카메라 추론/장치 생명주기 재설계, 학습 화면 전면 개편.
- 키보드·안구 저장/통계, 새 건강 위험도/의학 판정, AI 호출·요약 생성.
- 인증 시스템 교체, 원격 서버 구축·실제 전송·동기화 충돌 해결·배포.
- 기존 MySQL/SQL 자료 삭제, 실제 사용자 DB 초기화, 다른 페이지 전면 실데이터화.
- 영상·이미지·원시 랜드마크·비밀번호 저장, 자동 데이터 보존기간 만료 삭제.

## 6. 유지해야 하는 계약과 불변 조건

- 공개 API: 기존 `/api/auth`, `/api/sessions`, `/api/statistics`, `/health` 변경 없음. 기존 정수 score/alertCount 필드에 새 버전 데이터를 억지로 맞추지 않는다.
- 데이터베이스와 데이터: 새 DB는 `app.getPath('userData')/database/posture.sqlite` 제안. 기존 DB와 localStorage 계정은 보존. `server/schema.sql`, `front/database_schema.sql` 실행/삭제 안 함. 예시 이력은 실측으로 마이그레이션하지 않는다.
- 이벤트와 메시지: DB 경로·임의 SQL을 renderer에 제공하지 않는다. 새 `motiRecords` 전용 IPC에서 입력 크기/값/모드/소유자/호출 창을 검사한다. 기존 키보드 계약은 유지한다.
- 설정과 환경변수: 비밀값 변경 없음. 런타임은 현 잠금 기준, 새 드라이버가 필요하면 npm만 사용한다.
- 기존 사용자 동작: 시작/중지/기준 다시 잡기/장치 변경/모드 이동 유지. 저장 지연으로 카메라 해제나 화면 이동을 막지 않는다.
- 점수는 잠정 v1 기준 자세 유사도다. 서로 다른 모드·점수 정책 버전을 한 평균이나 ‘개선’으로 섞지 않는다.
- 관측시간과 실행시간의 정의, 500ms 유효 간격, 0점/null 구분은 `docs/evaluation.md`와 기존 테스트를 따른다.

## 8. 제안하는 구현 단계

### 단계 1: 저장 계약과 모드별 기록 모델

- 결과: 버전 있는 저장 DTO, 순수 검증, 목·어깨 매핑, 집계 시간 정의.
- 변경 예상 파일: `database/contracts.ts`, 검증 모듈, `features/records/modes/`, 관련 테스트.
- 구체적인 변경: 기록 ID, 로컬 소유자 ID, mode, run/segment ID, UTC 시작/종료·캡처 시각과 저장 당시 시간대, 종료 사유, 정책 버전, 실행/유효시간, 점수 적분합, 최장 연속 관찰, 이탈 횟수/시간, 시간 버킷을 정의한다.
- 유지할 계약: 영상/비밀번호 없음; 원평균을 반올림하여 저장하지 않음; 서로 다른 기준/버전 누적 구간 분리.
- 테스트와 명령: 프로젝트 Node의 `--test tests/record-contracts.test.mjs`, `npm run check`.
- 성공 기준: null/0·잘못된 수치·금지 모드·과대 payload·순번/시간 오류를 판별하고 JSON 왕복에 의미가 유지됨.
- 위험: 기존 Snapshot만으로 정확한 시간대 경계가 부족함. 캡처 시각과 누적 점수합 전달 계약을 먼저 고정한다.
- 중지/롤백: 계약과 테스트만 제거 가능, 아직 사용자 DB 생성 없음.
- 다음 단계 의존성: 계획 및 ADR 승인 필요.

### 단계 2: SQLite 저장·마이그레이션·복구

- 결과: 실제 파일 DB의 안전한 저장/읽기/재시도와 버전 검사.
- 변경 예상 파일: `database/sqlite/`, 관련 테스트, 필요한 경우 front 의존성/빌드 설정.
- 구체적인 변경: 단일 쓰기 소유자, 직렬 트랜잭션, 외래키/고유키, 잠금 대기 한도, 스키마 버전, 기존 파일 무결성 검사, 비파괴 migration. 짧은 배치로 커밋하며 미래 전송 DTO를 재구성할 기록 ID/순번을 보존한다.
- 유지할 계약: 손상/미지원 미래 버전 DB는 덮어쓰거나 자동 재생성하지 않음. 읽기 전용/디스크 오류를 구분한다.
- 테스트와 명령: `node --test tests/record-database.test.mjs`; 테스트 전용 임시 파일에 실제 SQL 실행.
- 성공 기준: commit 전 실패는 원복; 응답 유실 후 재시도·동시 쓰기에도 중복 없음; 재열기 데이터 동일; integrity/foreign key 검사 통과.
- 위험: Electron 내장 Node와 프로젝트 Node가 다르다. 드라이버는 양쪽 런타임·패키징 검증 후 확정한다. 내장 SQLite 사용 가능성을 먼저 검증하고 지원 불가 시 드라이버 선택을 ADR에 반영한다.
- 중지/롤백: 연결 중단 후 원본 보존. migration 전 백업; 자동 down migration이나 테이블 삭제 금지.
- 다음 단계 의존성: 단계 1 완료.

### 단계 3: Electron 저장·조회 IPC 연결

- 결과: 앱 전용 저장소 API와 renderer adapter. 개발 브라우저에서는 사용 불가를 명시한다.
- 변경 예상 파일: `front/electron/main.ts`, `preload.ts`, 관련 타입, `features/records/`.
- 구체적인 변경: DB 수명 관리, 현재 창/프레임 검사, 소유자별 조회/저장, 페이지 크기 제한, 저장/오류 결과, 앱 중복 실행의 쓰기 충돌 방지.
- 유지할 계약: renderer의 임의 파일 경로/SQL 실행 불가; 키보드 시작/중지 영향 없음.
- 테스트와 명령: IPC 검증 단위/통합, `npm run check`, `npm run build`, 빌드된 Electron SQLite smoke test.

## 11. 배포와 호환성

- 배포 순서: 로컬 구현/테스트→Electron 빌드/저장 재실행→별도 승인 시 배포. 이번 요청으로 원격 배포하지 않는다.
- 이전 버전과 동시 실행: 동일 DB 동시 쓰기를 방지하고 미지원 schema는 거절한다. 이전 앱은 새 SQLite를 모르므로 조회할 수 없다.
- feature flag: 별도 범용 플래그 체계는 추가하지 않는다. 저장소 초기화 실패/IPC 부재 시 기능 불가 표시.
- 데이터 마이그레이션: 새 파일과 스키마 버전 사용. 기존 MySQL/예시 배열 자동 이관 없음. 이미 같은 경로의 파일이 있으면 확인/백업 후 비파괴 migration만 적용한다.
- 운영 관측: 기록/저장 실패/미종료 상태, DB/schema 버전과 무결성 검사 결과. 원시 영상/계정 비밀번호 로그 금지.
- 전체 롤백 가능 여부: 코드 rollback 가능, 새 SQLite 파일 보존. 사용자가 앱에서 삭제한 데이터는 자동 복원 불가. 자동 downgrade 없음.
