# 16. 최종 승인 체크

> 병합 또는 배포 전 사용자가 작성한다. 기술 세부사항보다 증거와 미확인 범위가 투명한지 판단한다. 주석 속 예시는 참고용이다.

## 변경 확인

<!-- 예: 중복 결제 방지 요청과 실제 변경이 일치하고, 환불·새 결제사·전체 화면 개편은 포함되지 않았다. -->

- [ ] 요청한 결과와 실제 변경이 일치한다.
- [ ] 요청하지 않은 큰 변경이 포함되지 않았다.
- [ ] 변경 전과 변경 후를 설명할 수 있다.

## 검증 확인

<!-- 예: 결제 테스트와 타입 검사는 통과했고, 실제 결제사 운영 환경 테스트는 미실행으로 기록되어 있다. -->

- [ ] 실제 실행한 테스트와 결과가 기록되어 있다.
- [ ] 실행하지 않은 검사가 명확하다.
- [ ] 독립 리뷰의 심각한 지적이 해결되었거나 승인된 예외다.
- [ ] 기존 테스트를 삭제하거나 약화해 통과시킨 것이 아니다.

## 이해 확인

<!-- 예: 요청 진입점, 상태가 바뀌는 함수, 가장 위험한 실패, 확인하지 못한 모바일 동작을 알고 있다. -->

- [ ] 진입점을 알고 있다.
- [ ] 중요한 상태 변경 위치를 알고 있다.
- [ ] 가장 위험한 실패를 알고 있다.
- [ ] 아직 모르는 부분을 알고 있다.

## 운영 확인

<!-- 예: 기능 플래그를 단계적으로 켜고 pending 지표를 보며, 문제 시 플래그를 끄고 이전 버전으로 롤백한다. -->

- [ ] 배포 순서가 있다.
- [ ] 문제 발견 방법이 있다.
- [ ] 중지 또는 롤백 방법이 있다.
- [ ] 필요한 담당자 승인을 받았다.
