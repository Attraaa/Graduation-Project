# 개발을 모르는 사용자를 위한 빠른 시작

이 키트를 사용하기 위해 코드를 작성하거나 Git 명령을 알 필요는 없다. 사용자는 문제와 원하는 결과를 설명하고, AI가 만든 계획과 결과에서 중요한 내용만 확인하면 된다.

> 작업 문서는 저장소에 커밋되어 팀원에게 공유될 수 있다. 비밀번호, API 키, 접근 토큰, 실제 카드 정보, 주민등록번호, 고객의 실제 개인정보를 넣지 않는다. 필요한 경우 마스킹된 예시나 내부 이슈 링크만 기록한다.

## 먼저 알아둘 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 저장소(repository) | 프로젝트의 코드와 문서를 함께 보관하는 폴더 |
| 브랜치(branch) | 본래 코드에 바로 섞지 않고 따로 작업하는 복사된 작업선 |
| 커밋(commit) | 현재까지의 변경을 이름과 함께 저장한 체크포인트 |
| diff | 이전과 비교해 추가·삭제·수정된 내용 |
| PR(Pull Request) | 작업한 변경을 본래 코드에 합쳐달라고 요청하는 검토 문서 |
| 테스트 | 변경이 원하는 대로 작동하고 기존 기능을 깨지 않는지 확인하는 자동 검사 |
| ADR | 중요한 설계 방법을 왜 선택했는지 남기는 결정 기록 |
| 롤백 | 문제가 생겼을 때 이전 상태로 되돌리는 것 |
| API | 화면이나 다른 시스템이 서버에 요청하고 답을 받는 약속 |
| DB/데이터베이스 | 주문, 사용자, 결제 같은 정보를 저장하는 곳 |
| 배포 | 변경한 코드를 실제 사용 환경에 적용하는 것 |

모르는 용어가 더 나오면 AI에게 다음처럼 묻는다.

```text
이 문서에 나온 [용어]를 개발을 모르는 사람이 이해할 수 있게 설명해 주세요.
이번 작업에서 왜 중요한지와 잘못되면 어떤 문제가 생기는지만 알려주세요.
```

# 새 작업을 시작하는 가장 쉬운 방법

## 1. AI에게 작업 폴더를 만들어 달라고 한다

아래 문장을 복사하고 대괄호 부분만 바꾼다.

```text
새 작업을 시작하려고 합니다.

작업 이름: [예: 결제 버튼을 두 번 눌렀을 때 중복 결제 방지]
해결하려는 문제: [예: 화면이 멈추면 사용자가 다시 눌러 결제가 두 번 될 수 있음]
관련 이슈: [없으면 없음]
현재 담당자: [내 이름 또는 미정]

`ai/00_INITIALIZE_WORK_ITEM.md`와
`templates/WORK_ITEM_STATUS_TEMPLATE.md`를 사용해 작업 폴더를 초기화하세요.

아직 코드를 수정하거나 커밋하지 마세요.
생성한 파일과 내가 다음으로 작성할 파일만 알려주세요.
```

## 2. 문제 설명 파일을 작성한다

작업 폴더에 복사된 `01_TASK_INPUT.md`를 작성한다. 무엇을 써야 할지 모르겠다면 각 항목 바로 아래의 `<!-- 예: ... -->` 주석을 참고한다. Markdown 미리보기에서는 이 주석이 보이지 않으므로 편집 화면에서 확인한다.

기술적인 위치나 해결 방법을 모르면 `AI 조사 필요`라고 쓴다.

## 3. AI에게 계획만 요청한다

```text
내가 작성한 작업 폴더의 `01_TASK_INPUT.md`를 읽으세요.

다음을 적용하세요.

- `ai/02_PLAN_DRAFT_INSTRUCTIONS.md`
- `templates/03_PLAN_TEMPLATE.md`

템플릿 각 항목의 주석 예시와 비슷한 상세 수준으로
작업 폴더의 `03_PLAN.md`를 작성하세요.

아직 코드는 수정하지 마세요.
```

## 4. 계획을 확인한다

작업 폴더의 `04_PLAN_REVIEW.md`를 작성한다. 기술 파일명보다 다음을 확인한다.

- 내가 말한 문제가 맞는가?
- 원하지 않은 기능이 추가되었는가?
- 돈, 데이터, 권한, 기존 사용자 위험이 있는가?
- 한 번에 너무 많은 것을 바꾸는가?
- 테스트와 되돌리는 방법이 있는가?

이해하지 못한 부분은 조건부 승인 또는 보류로 표시한다.

## 5. 한 단계만 구현하게 한다

```text
계획 검토 문서를 반영해 최종 계획을 정리하세요.
내가 승인한 [단계 번호와 이름]만 구현하세요.

`ai/07_IMPLEMENT_ONE_STEP.md`를 적용하세요.
다른 단계는 아직 구현하지 마세요.
```

각 단계가 끝날 때 테스트 결과와 `STATUS.md`가 갱신되었는지 확인한다.

# AI가 작업을 끝냈다고 할 때 묻는 말

```text
작업 완료라고 판단한 근거를 보여주세요.

1. 실제로 변경한 파일
2. 변경 전과 변경 후
3. 실행한 테스트 명령과 실제 결과
4. 실행하지 못한 검사
5. 아직 확인하지 못한 부분
6. 가장 위험한 실패
7. 문제가 생길 때 되돌리는 방법
8. 현재 STATUS.md와 실제 Git 상태의 일치 여부
```

`문제없습니다`, `테스트했습니다`, `안전합니다` 같은 짧은 답만 있으면 구체적인 근거를 다시 요청한다.

# 변경 내용을 이해하는 가장 쉬운 방법

작업 폴더의 `13_UNDERSTANDING.md`를 연다. 빈칸을 직접 채우려고 해보고, 모르는 항목만 AI에게 질문한다.

```text
작업 폴더의 `13_UNDERSTANDING.md`에서 다음 항목을 채우지 못했습니다.

[모르는 항목 붙여넣기]

`ai/14_CODE_UNDERSTANDING_INSTRUCTIONS.md`를 사용해 설명하세요.
전문 용어를 줄이고 최대 5단계로 설명해 주세요.
실제 파일과 함수 근거도 함께 알려주세요.
```

내가 작성한 내용을 검토받을 때:

```text
아래는 내가 이해한 내용입니다.

[내가 작성한 내용]

`ai/15_UNDERSTANDING_FOLLOWUP.md`를 사용해 실제 코드와 테스트를
기준으로 틀린 부분과 빠진 부분을 교정하세요.
무조건 동의하지 마세요.
```

# 다른 사람이 이어서 작업할 때

새 담당자에게 긴 AI 대화 전체를 전달할 필요는 없다. 작업 폴더와 브랜치를 전달하고 다음 요청을 사용한다.

```text
이 작업을 이어받으려고 합니다.

작업 폴더: [작업 폴더 경로]

작업 폴더의 `STATUS.md`와 `ai/00_RESUME_WORK_ITEM.md`를 읽으세요.
현재 브랜치, 마지막 커밋, 미커밋 파일, 결과 문서, 테스트 결과를
실제 저장소와 비교하세요.

아직 코드는 수정하지 말고 다음만 설명하세요.

1. 어디까지 완료되었는지
2. 실제 저장소와 상태 파일이 다른 부분
3. 아직 끝나지 않은 일
4. 다음으로 해야 할 한 단계
5. 진행 전에 필요한 승인
```

AI가 상태가 일치한다고 확인하고 사용자가 다음 단계를 승인한 후 작업을 재개한다.

# 언제 사람 전문가에게 확인해야 하나

다음은 AI 설명만으로 승인하지 않고 담당 개발자 또는 전문가 확인을 받는다.

- 실제 금액이 오가는 결제
- 사용자 로그인과 권한
- 개인정보
- 데이터 삭제
- DB 구조 변경
- 많은 기존 데이터를 한꺼번에 변경
- 배포 순서가 중요한 작업
- 되돌릴 수 없는 변경
- AI가 `확인 필요`라고 표시한 중요 계약

이때는 다음처럼 요청한다.

```text
정상 흐름과 테스트 결과는 확인했습니다.
다만 [구체적으로 모르는 부분]은 판단하지 못했습니다.
이 부분이 데이터/결제/권한에 어떤 영향을 주는지 담당자 검토가 필요합니다.
```

모르는 부분을 정확히 표시하는 것은 실패가 아니라 안전한 작업 관리다.
