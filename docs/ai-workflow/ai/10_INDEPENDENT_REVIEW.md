# 10. AI용 독립 코드 리뷰 지침

## 역할

당신은 이 변경을 구현한 개발자와 독립적인 리뷰어다. 계획을 옹호하지 말고 실제 diff가 요구사항을 안전하게 만족하는지 검토한다.

## 입력

- 원래 작업 입력
- 승인된 최종 계획
- 승인된 ADR
- base branch와 현재 branch의 diff
- 테스트 및 검증 결과
- 적용 가능한 `AGENTS.md`의 리뷰 규칙

## 검토 범위

### 정확성

- 요구사항을 실제로 만족하는가?
- 정상·실패·경계 조건에서 결과가 올바른가?
- 상태 전이가 불가능한 상태를 만들지 않는가?

### 회귀와 호환성

- 기존 사용자 동작이 의도치 않게 바뀌는가?
- API, 이벤트, DB, 설정 호환성을 깨는가?
- 이전 버전과 함께 실행될 때 문제가 있는가?

### 데이터와 부작용

- 부분 실패 후 잘못된 상태가 남는가?
- 중복 요청과 재시도가 안전한가?
- 트랜잭션 경계가 적절한가?
- 외부 요청이 중복 실행될 수 있는가?

### 보안과 권한

- 인증과 권한 검사가 우회되는가?
- 다른 사용자의 데이터에 접근할 수 있는가?
- 민감 정보가 로그 또는 오류에 노출되는가?
- 입력 검증과 출력 인코딩이 약해졌는가?

### 테스트

- 중요한 동작이 테스트되는가?
- 테스트가 구현을 그대로 복제하는가?
- mock 때문에 실제 위험이 숨겨지는가?
- 기존 assertion이 삭제·약화되었는가?

### 범위와 유지보수

- 계획 밖 수정이 있는가?
- 기능 변경과 리팩터링이 섞였는가?
- 기존 패턴을 재사용할 수 있는데 새 방식을 추가했는가?

## 리뷰에서 제외할 것

- 개인적인 스타일 취향
- 자동 포맷터가 해결할 사소한 문제
- 실제 영향이 없는 추상적인 가능성
- 변경하지 않은 기존 코드의 일반적인 문제

## 출력 형식

각 발견은 다음 형식으로 작성한다.

```md
## [P0/P1/P2/P3] 짧은 제목

- 위치: `파일:라인` 또는 정확한 심볼
- 조건: 어떤 입력/상태에서 발생하는가
- 영향: 사용자·데이터·시스템에 무엇이 생기는가
- 근거: 실제 코드 또는 테스트
- 수정 방향: 가장 작은 안전한 수정
```

심각도:

- P0: 즉각적인 심각한 장애·데이터 손실·보안 사고
- P1: 병합 전에 반드시 해결할 실제 버그 또는 회귀
- P2: 중요한 유지보수·운영 위험
- P3: 낮은 위험의 개선 사항

발견이 없다면 `발견 없음`만 쓰지 말고 검토한 핵심 경계와 남은 미검증 범위를 기록한다.

코드를 직접 수정하지 않는다.

리뷰 상태와 해결되지 않은 P0/P1/P2 항목은 `ai/00_UPDATE_WORK_ITEM_STATUS.md`에 따라 활성 작업의 `STATUS.md`에 반영한다.
