# 06. AI용 ADR 필요 여부 판단 및 초안 지침

## 역할

승인된 계획에 장기적인 설계 결정이 있는지 판단하고, 필요한 경우 ADR 초안을 만든다. 이 단계에서는 해당 결정을 구현하지 않는다.

## ADR이 필요한 기준

다음 중 하나 이상이면 ADR을 우선 고려한다.

- 여러 모듈 또는 팀의 책임 경계가 바뀐다.
- 공개 API, 이벤트, 데이터 스키마가 장기적으로 바뀐다.
- 인증·권한·보안 모델이 바뀐다.
- 핵심 dependency, 프레임워크, 저장소 또는 통신 방식을 선택한다.
- 동기/비동기, 캐시, 재시도, idempotency, 동시성 전략을 선택한다.
- 되돌리기 어렵거나 마이그레이션 비용이 크다.
- 여러 합리적인 대안이 있고 장단점이 다르다.
- 향후 개발자가 선택 이유를 다시 물을 가능성이 높다.

다음만으로는 일반적으로 ADR이 필요하지 않다.

- 기존 승인 패턴을 그대로 적용
- 작은 버그 수정
- 지역적인 구현 상세
- 쉽게 되돌릴 수 있는 이름 또는 구조 변경
- 자동 포맷팅

## 수행 절차

1. 계획에서 설계 결정을 추출한다.
2. 각 결정에 대해 ADR 필요 기준을 적용한다.
3. ADR이 필요 없으면 이유를 구체적으로 기록한다.
4. ADR이 필요하면 `templates/ADR_TEMPLATE.md`를 복사한 형식으로 새 ADR 초안을 작성한다.
5. 현 상태 유지를 포함해 최소 두 가지 대안을 비교한다.
6. 알려지지 않은 운영·비용·보안 가정을 명시한다.
7. 결정을 임의로 Accepted로 만들지 않는다.

## 출력 A: ADR이 필요 없는 경우

```md
## ADR 판단

- 결과: 불필요
- 이유:
- 기존에 따르는 결정/패턴:
- 변경이 지역적이고 가역적인 근거:
```

## 출력 B: ADR이 필요한 경우

- 새 파일 이름을 제안한다. 예: `docs/adr/0007-payment-idempotency.md`
- 상태는 `Proposed`로 둔다.
- `templates/ADR_TEMPLATE.md`의 모든 관련 항목을 채운다.
- 정보가 없는 항목은 `확인 필요`로 표시한다.

ADR을 작성한 후 다음 선언으로 종료한다.

```text
ADR 상태: Proposed
프로덕션 구현: 승인 전 보류
사람이 결정해야 할 항목: ...
```
