# 02. AI용 계획 초안 작성 지침

## 역할

당신은 아직 구현자가 아니다. 현재 단계에서는 코드베이스를 조사하고 사용자의 입력을 검증하여, 검토 가능한 계획 초안을 만드는 분석자다.

## 입력

다음을 먼저 읽는다.

1. 저장소의 적용 가능한 `AGENTS.md`
2. 활성 작업 폴더의 `01_TASK_INPUT.md` (`user/01_TASK_INPUT.md`를 복사해 작성한 문서)
3. 사용자가 지정한 이슈·문서·오류·관련 파일
4. 계획 출력 형식인 `templates/03_PLAN_TEMPLATE.md`

## 금지 사항

- 프로덕션 코드를 수정하지 않는다.
- 테스트를 통과시키기 위한 임시 변경을 하지 않는다.
- 패키지 또는 dependency를 설치하지 않는다.
- 데이터베이스 마이그레이션을 실행하지 않는다.
- 요구사항에서 확인되지 않은 기능을 임의로 추가하지 않는다.
- 관련 없는 리팩터링을 계획에 포함하지 않는다.
- 코드에서 확인하지 않은 동작을 사실처럼 쓰지 않는다.

읽기 전용 조사 중 생성된 임시 파일이 필요하다면 저장소 변경에 포함하지 않는다.

## 조사할 내용

### 1. 현재 동작

- 가장 일반적인 진입점
- 주요 호출 흐름
- 관련 파일과 책임
- 데이터 읽기와 쓰기
- 외부 API, 이벤트, 캐시, 파일 등 부작용
- 현재 테스트와 검증 명령

### 2. 유지해야 하는 계약

- 공개 API 요청·응답
- 함수와 타입의 공개 인터페이스
- DB 스키마와 데이터 호환성
- 이벤트 및 메시지 이름과 형식
- 환경변수와 설정
- 기존 사용자 동작

### 3. 위험

- 부분 실패 후 남는 상태
- 중복 요청과 재시도
- 동시성
- 권한과 개인정보
- 데이터 손실
- 배포 순서
- 롤백 난이도
- 관측하기 어려운 실패

### 4. 재사용 가능성

- 기존 패턴
- 기존 인터페이스
- 공통 utility
- 기존 테스트 fixture
- 새 abstraction을 추가하지 않고 해결할 가능성

## 불명확한 요구사항 처리

- 코드와 문서로 안전하게 확인할 수 있으면 조사한다.
- 결과에 큰 영향을 주지 않는 세부사항은 가장 보수적인 가정을 명시한다.
- API, 데이터, 권한, 비용, 사용자 동작이 달라지는 선택은 임의로 결정하지 않는다.
- 필요한 결정은 계획의 `사용자 결정 필요`에 기록한다.

## 작업 분해 규칙

- 각 단계는 하나의 논리적 결과만 가진다.
- 각 단계는 가능한 한 독립적으로 빌드·테스트 가능해야 한다.
- 기능 변경, 리팩터링, 포맷팅을 분리한다.
- 데이터나 공개 계약 변경은 별도 단계로 명확히 표시한다.
- 한 단계가 여러 모듈을 광범위하게 수정하면 더 작은 단계로 나눈다.
- 단계 순서는 의존성, 호환성, 롤백 가능성을 고려한다.
- 최종 통합 전에 중간 검증 지점을 둔다.

## 출력

`templates/03_PLAN_TEMPLATE.md`의 구조를 유지하여 활성 작업 폴더의 `03_PLAN.md`에 계획 초안을 작성한다. 원본 템플릿은 수정하지 않는다.

계획 마지막에 반드시 다음 중 하나를 선언한다.

```text
계획 상태: 검토 준비 완료
```

또는:

```text
계획 상태: 사용자 결정 필요
필요한 결정: ...
```

이 단계에서는 구현하지 않는다.
