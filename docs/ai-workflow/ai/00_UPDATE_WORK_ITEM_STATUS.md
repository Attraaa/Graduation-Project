# 00-C. AI용 작업 상태 갱신 지침

## 역할

각 단계가 끝나거나 작업이 중단·인계될 때 작업 폴더의 `STATUS.md`를 실제 저장소 상태에 맞게 갱신한다. 상태 갱신만 요청받은 경우 프로덕션 코드를 수정하지 않는다.

## 갱신 시점

- 작업 폴더 초기화 후
- 작업 입력 완료 후
- 계획 초안 작성 후
- 계획 승인 또는 수정 요청 후
- ADR 제안·승인·보류 후
- 구현 단계 시작과 완료 후
- 테스트와 검증 후
- 독립 리뷰와 리뷰 수정 후
- 커밋 후
- 담당자 인계 전
- 차단 사유가 생기거나 해결된 후
- PR 생성·승인·병합 후
- 작업 취소 후

## 사실 확인

상태 파일을 수정하기 전에 가능한 범위에서 다음을 실제로 확인한다.

- 현재 브랜치
- HEAD 커밋
- staged, unstaged, untracked 변경
- base branch와의 관계
- 결과 파일 존재 여부
- 최근 테스트 결과가 적용되는 코드 버전
- 해결되지 않은 리뷰 지적

## 반드시 갱신할 항목

1. 작업 상태
2. 현재 단계
3. 마지막 완료 단계
4. 다음 행동
5. 현재 담당자와 작업 잠금
6. 마지막 갱신 시각
7. 진행 체크포인트
8. 구현 단계 진행 표
9. 마지막 저장소 상태
10. 미해결 질문과 차단 사유
11. 다음 사람이 시작할 위치
12. 상태 변경 기록

## 상태 전환 원칙

- 결과 문서나 검증 증거가 없으면 단계를 완료로 표시하지 않는다.
- 코드를 작성했지만 테스트하지 않았다면 `IMPLEMENTING` 또는 `VERIFYING`이다.
- 테스트를 통과했어도 독립 리뷰 전이면 `REVIEWING`이 아니다.
- P0/P1 지적이 남아 있으면 `READY_TO_MERGE`로 표시하지 않는다.
- 외부 결정이나 권한을 기다리면 `BLOCKED`와 구체적인 해결 조건을 쓴다.
- 병합되지 않은 작업을 `DONE`으로 표시하지 않는다.

## 커밋과 상태 파일

- 가능하면 상태 파일은 상태가 설명하는 코드·테스트·결과 문서와 같은 커밋에 포함한다.
- 상태 파일에 아직 존재하지 않는 커밋 ID를 미리 쓰지 않는다.
- 커밋 직후에는 상태 파일의 HEAD를 갱신할 필요가 생길 수 있다. 팀이 문서 전용 후속 커밋을 원하지 않으면 `관련 커밋`은 단계 보고나 PR 시스템에서 확정하고, 상태 파일에는 마지막 확인 시점의 ID를 기록한다.
- 미커밋 변경이 있으면 파일 목록을 숨기지 않는다.

## 출력

상태 파일 갱신 후 다음을 보고한다.

```md
## 상태 갱신

- 이전 상태:
- 새 상태:
- 마지막 완료 단계:
- 다음 행동:
- 현재 브랜치/HEAD:
- 미커밋 변경:
- 차단 사유:
- 갱신한 상태 파일:
```
