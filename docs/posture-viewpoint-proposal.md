# 고개 회전·카메라 높이 대응 검토와 알람 현황

2026-10-19. **제안 문서이며 회전/카메라 높이 처리와 알람 코드는 이번에 변경하지 않았습니다.** 이번 구현은 [점수 감도 설정](posture-score-tuning.md)만 조정합니다.

## 현재 측정이 멈추는 이유

- `calibration.ts`/`observation.ts`: `abs(코 x - 양 귀 중점 x) / 귀 폭 > 0.15`이면 고개 회전으로 보류합니다. 이 값은 각도가 아니며 눈동자가 화면을 보는지는 검사하지 않습니다. 양 귀가 가려지거나 귀 폭이 줄면 기존 목 전진 산식의 오차가 커질 수 있어 둔 보호입니다.
- 코·양 귀·양어깨의 visibility가 0.7 미만, 필요한 점이 화면 밖, 귀/어깨 폭 부족, 추정 양어깨 깊이 차이가 너무 큰 경우에도 보류합니다. 상체 화면은 이 중 여러 원인에 같은 ‘정면을 향해 주세요’ 안내를 사용합니다.
- **카메라 높이 자체나 머리의 상하 각도를 검사해 멈추는 전용 조건은 없습니다.** 위·아래 카메라에서 본 현상을 같은 회전 오류라고 단정할 수 없습니다. 귀/어깨 가림·좌표 신뢰도·구도 변화일 수 있으므로 `snapshot.reason`, 각 필수 점의 visibility, yaw 비율을 먼저 확인해야 합니다.
- 보류되는 것은 주로 목·어깨 점수이며, 같은 카메라의 안구 분석은 별도 엔진입니다. 각 엔진의 품질 조건을 구분해서 진단해야 합니다.

## 1. 약간 고개를 돌린 상태 — 권장 방안

1. **기존 Face Landmarker의 얼굴 방향 추정을 재사용합니다.** 현재 `EyeMonitor.tsx`는 blendshape를 켜지만 얼굴 변환 행렬은 요청하지 않습니다. `outputFacialTransformationMatrixes`를 활성화하는 실험으로 좌우/상하/기울기 방향을 추정하고 개인 기준과 비교하는 것이 첫 후보입니다. 공식 행렬은 표준 얼굴을 검출 얼굴로 변환하는 용도이며, 이 출력을 Moti의 방향 품질 검사에 사용하는 것은 검증이 필요한 설계 제안입니다. [Google 공식 옵션 설명](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js)
2. **허용 회전 범위 안에서는 회전에 덜 민감한 특징으로 목 전진을 계산합니다.** 얼굴의 회전/투영 변화와 머리의 상대 이동을 분리하고, 회전 때문에 줄어든 귀 폭을 직접 전진 신호로 사용하지 않습니다. 단순히 yaw 제한만 높이거나 귀가 사라진 것을 0 변화로 채우면 오판정 위험이 있습니다. 우선 좌우 0/10/20도에서 비교하고 채택 범위는 실측 결과로 결정합니다.
3. **Face/Pose 좌표를 바로 더하지 않습니다.** 두 추론의 좌표계/원점/깊이 스케일이 다르므로 같은 변환 영상·동일 캡처 시각의 결과를 연결하고 이미지 공간의 어깨 기준으로 정규화하는 별도 계약이 필요합니다. 회전 행렬의 이동 성분을 실제 cm 거리로 쓰지 않습니다.
4. **부위별로 품질을 나눕니다.** 귀가 안 보여 목을 판정하기 어려워도 양어깨가 안정적으로 보이면 어깨 기울기는 관측할 수 있습니다. 다만 현재 어깨 점수의 상하 항도 귀에 의존하므로 단순히 어깨 전체를 계속 계산하면 안 됩니다. ‘기울기만 관측 가능’ 정책/표시와 유효 시간 저장 계약을 먼저 정의해야 합니다.

사용자의 시선이 화면에 있는지 판정하는 기능은 별개입니다. 고개가 돌아갔어도 측정할 수 있게 만드는 데 눈동자 시선 추적이 반드시 필요한 것은 아닙니다. 새로운 대형 모델을 추가하기 전에 이미 실행 중인 얼굴 모델을 재사용하는 방안을 권합니다.

## 2. 모니터 위·아래 카메라 — 권장 방안

1. **실패 이유를 먼저 분리합니다.** 고정된 카메라에서 평소 화면을 보는 편한 자세로 새 기준을 수집하고, 시작/측정 각각 어떤 품질 조건에서 막히는지 확인합니다. 단순 고정 오프셋은 개인 기준이 일부 흡수하지만 투영 변화나 가림까지 보정하지는 못합니다.
2. **카메라별 자연스러운 시선 높이를 기준으로 수집합니다.** 렌즈를 직접 응시하도록 강제하는 대신 평소 화면을 볼 때의 얼굴 pitch/yaw와 어깨 관계를 함께 기록하는 방식입니다. 얼굴 pitch만으로 카메라 설치 높이를 알아낼 수는 없으므로 ‘중립 자세에 대한 상대 방향 기준’으로 다룹니다. 카메라를 옮기거나 영상 구도를 바꾸면 재수집하고, 실제 목 전진을 새로운 정상 기준으로 계속 흡수하는 자동 보정은 하지 않습니다.
3. **머리–어깨 상대 특징을 투영 조건별로 검증합니다.** 동일한 자세의 카메라 높이 변화와 실제 머리 전진을 구별해야 합니다. 정면/상단/하단 카메라, 두 거리, 좌우 회전 유무에서 중립·머리만 전진·몸 전체 접근·어깨 기울임을 비교합니다. 각 조건에서 점수 편차, 보류율, 목 전진 누락률과 복귀 지연을 함께 기록합니다.
4. **귀가 지속적으로 가려지는 구도는 다른 얼굴 특징의 대체 가능성을 검증합니다.** 가시성 제한을 내리는 것만으로는 잘못 잡은 좌표까지 통과합니다. 관측 가능한 특징만으로 별도 점수 정책을 만들거나 관측 불가를 유지해야 합니다.

MediaPipe의 world 좌표도 이미지에서 추정한 3D 관절입니다. 따라서 원근과 가림의 영향을 자동으로 제거하는 센서 좌표로 취급하지 않습니다. [Pose 공식 모델 설명](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker)

## 3. 학습했던 데이터로 해결할 수 있는가

현재 분류기는 MultiPosture의 코·어깨·골반 7특징으로 몸통 upright/forward/backward/lateral을 구분합니다. 공개 데이터 설명도 몸통/하체 자세 라벨이며, 원본 영상은 제공하지 않습니다. **현재 학습에는 얼굴 방향·화면 시선·카메라 설치 높이·목 전진 정답을 사용하지 않았습니다.** 따라서 모델을 다시 켜거나 가중치를 높이는 것만으로 이 문제를 해결할 근거가 없습니다. [MultiPosture 원자료](https://zenodo.org/records/14230872), [현재 모델 카드](posture-model-card.md)

3D 좌표를 회전시킨 증강은 이상적인 좌표계 변화에 대한 실험으로는 가능하지만, 실제 상단/하단 영상에서 발생하는 귀 가림과 MediaPipe 추정 오류를 재현하지 않습니다. 먼저 위의 상대 기준·얼굴 방향 보정을 실험하고, 부족할 때 실제 Moti 구도의 새 자료로 골반 없는 보조 모델을 학습하는 순서가 적합합니다. 학습/검증은 사람·세션 단위로 나누고 기존 정면 성능이 나빠지지 않는지 함께 확인해야 합니다.

## 4. 실제 가동되는 알람 현황

| 항목 | 현재 코드 상태 |
| --- | --- |
| 자세 경고 켜기/빈도/세기/경고 점수 | `Settings.tsx`가 `postureAI.notifications`, `alertFrequency`, `alertStrength`, `scoreThreshold`를 localStorage에 저장. 실제 측정 런타임에서 읽어 알림을 보내는 경로는 없음 |
| Windows 알림·트레이 경고·경고음 | 프론트/Electron에 점수 조건과 연결된 Notification/Tray/오디오 호출 없음. 자동 자세 알람으로 동작하지 않음 |
| 눈이 열린 상태 15초, 기준 대비 얼굴 크기 1.25배가 3초 지속 | `measurement.ts`가 `openReminder`/`nearReminder`를 계산하고 `EyeRecorder`가 조건 진입 횟수를 저장함. 현재 상체 카드·화면은 이 플래그를 안내로 표시하지 않음 |
| 통계·학습이력의 ‘안내 횟수’ | 위 내부 조건 횟수를 조회함. 실제 사용자에게 알림을 전달한 횟수라는 뜻은 아님 |
| 화면의 카메라/추적 오류, 기준 수집·복귀 안내 | 현재 표시됨. 자세 점수에 따른 경고 알람과는 다른 상태 안내 |

이전 `docs/eye-mode.md`의 독립 안구 화면 안내 설명에는 과거 동작이 섞여 있습니다. 현재 실행 경로는 `MonitoringProvider → EyeMonitor/PostureMonitor → PostureSession/PostureMetrics`입니다.

알람을 다음에 구현한다면 검증된 현재 점수·관측 가능 여부·지속 시간을 조건으로 사용하고, 알림 켜기/빈도/세기/중복 억제를 연결해야 합니다. 미관측·일시정지에는 경고를 만들지 않고, 조건 발생과 실제 전달 여부를 구분해서 기록하는 것이 좋습니다. 이번 요청에서는 현황 확인만 했습니다.
