# 보안 기준과 남은 검증

기준일: 2026-10-30. 현재 범위는 AI 총평의 API 키, 비용, 외부 전송 보안입니다. 프로젝트 전체의 보안 감사를 완료했다는 뜻은 아닙니다. 현재 구현은 [AI 총평](ai-review.md), 기존 결정은 [제품 결정 D7](product-decisions.md), 작업 목록은 [로드맵](roadmap.md)을 함께 확인합니다.

## 현재 구현과 적용 방향

- AI 총평은 로그인한 사용자의 요청을 Moti 서버가 받아, 서버 환경변수 `ANTHROPIC_API_KEY`로 Claude를 호출합니다. 사용자의 개인 API 키를 입력받거나 보관하는 BYOK 기능은 미구현입니다.
- 2026-10-17의 서버 키 사용 결정을 유지합니다. 졸업발표·사용성 테스트에서는 서버 제공 방식에 비용 통제를 보완하는 방향을 권장합니다. 개인 키 연결은 필요성을 확인한 뒤 검토할 선택 기능이며, 이번 문서화가 BYOK 구현 승인이나 완료를 뜻하지 않습니다.
- 서버는 기간 집계의 숫자와 허용된 키 코드만 검사해 AI에 보냅니다. 영상, 키 입력 원문, 계정 정보는 AI 요청에 포함하지 않습니다. 화면에서 전송 내용을 확인하고 사용자가 총평 생성을 요청합니다. 집계만 보낸다는 사실이 모든 개인정보 위험이 없다는 뜻은 아닙니다.
- 현재 계정당 시간당 10회 제한은 서버 메모리에 있어 재시작 시 초기화됩니다. 호출의 최대 출력은 16,000토큰이며 총평은 저장하지 않습니다. 화면을 벗어나 다시 생성하면 추가 호출이 발생할 수 있습니다.
- HTTPS는 저장소 문서상 후속 작업입니다. 이번에는 운영 서버의 TLS 설정, 실제 키, 결제 설정을 확인하지 않았으므로 배포 보안이나 비용 상한이 검증됐다고 표현하지 않습니다.

## API 키 관리 원칙

API 키는 호출과 과금을 허용하는 비밀 자격증명입니다. 사용자가 직접 비용을 내더라도 키 유출·무단 사용 위험과 앱의 보호 책임은 사라지지 않습니다. Anthropic도 제삼자 도구에 키를 제공할 때의 신뢰 문제와 사용량 감시, 비밀정보 관리를 안내합니다. [Anthropic API 키 보안 안내](https://support.claude.com/en/articles/9767949-api-key-best-practices-keep-your-keys-safe-and-secure)

| 방식 | 관리 책임과 위험 | Moti 적용 방향 |
| --- | --- | --- |
| 팀의 키를 서버에서 사용 | 팀이 서버 비밀정보와 전체 비용을 관리 | 현재 구현 유지, 외부 테스트 전 통제 보완 |
| 개인 키를 사용자 PC에 보관해 제공자에 직접 호출 | 앱이 안전한 저장·호출·삭제와 과금 안내를 구현 | 향후 필요성이 확인되면 선택 기능으로 검토 |
| 개인 키를 Moti 서버에 전송·보관 | 여러 사용자의 키에 대한 접근 통제·암호화·삭제·사고 대응이 필요 | 현재 채택하지 않음. 도입하려면 별도 설계·결정 필요 |

서버 키는 서버의 환경변수 또는 비밀정보 관리 수단으로만 주입합니다. `front/.env`, `VITE_*`, 배포 앱 번들, 저장소, 응답, 로그, 오류 보고에 넣지 않습니다. 키 접근 권한은 필요한 운영 주체로 제한하며, 노출 시 기존 키 폐기·교체와 사용량 확인 절차를 마련합니다. 키 값이나 실제 개인정보를 문서·테스트 자료에 기록하지 않습니다.

## 외부 사용성 테스트 전 남은 작업

아래는 **미완료 작업과 완료 기준**입니다. 기존 시간당 제한이나 제공자의 예산 알림만으로 완료 처리하지 않습니다.

| ID | 작업 | 완료 기준 |
| --- | --- | --- |
| SEC-AI-01 | 지속되는 사용자별 사용량 제한 | 일일·시간당 정책을 정하고 재시작·다중 서버·동시 요청에서도 한도가 유지됨을 검증. 한도 초과 시 제공자 호출 전에 차단 |
| SEC-AI-02 | 전체 예산과 호출 중단 | 테스트 인원·기간에 맞는 예산을 정하고 전체 사용량을 집계. 동시 호출·재시도·진행 중 요청 비용을 고려한 중단 기준과 운영자의 즉시 중단 수단 마련. 제공자 한도가 알림인지 실제 차단인지 별도 확인 |
| SEC-AI-03 | 불필요한 호출·출력 줄이기 | 중복 클릭·동시 요청·화면 재진입의 중복 호출 방지 정책과 재시도 상한을 검증. 짧은 총평에 맞는 출력 토큰 상한을 품질과 함께 검토. 결과 재사용을 도입하면 사용자 격리·보관 기간·삭제 정책도 결정 |
| SEC-AI-04 | 배포 HTTPS 검증 | 외부 앱↔Moti API와 서버↔AI 제공자 구간의 인증서·암호화 연결 확인. 로그인 자격증명·JWT·집계가 평문으로 전송되지 않고 인증서 검증을 우회하지 않음을 확인 |
| SEC-AI-05 | 비밀정보 유출 방지·대응 | 앱 번들·저장소·응답·로그·오류 보고에서 키 노출 여부 확인. 서버 비밀정보 접근 제한과 키 폐기·교체·사용량 점검 절차 검증. 검증에는 실제 키 대신 테스트용 표식 사용 |
| SEC-AI-06 | 전송 범위·과금 안내 검증 | 제공자·전송 집계·보관 여부를 화면에 안내. 허용된 집계 이외의 영상·입력 원문·계정 정보가 제공자 요청에 섞이지 않음을 검사. 운영 비용 부담과 사용자 이용 한도를 확정 |

정책 검증은 대역 클라이언트로 우선 수행하고, 실제 API 호출은 별도 테스트 예산과 키가 준비된 범위에서 진행합니다. 한도·보관 정책의 수치는 구현 전에 결정하며 이 문서만으로 임의의 운영 예산을 승인하지 않습니다.

## 개인 API 키 연결을 재검토할 때

BYOK는 사용자에게 제공자 가입·결제·키 발급을 요구하므로 일반 사용자 테스트의 진입 부담도 함께 평가합니다. 채택한다면 다음 조건을 설계·검증해야 합니다.

- 키는 사용자 기기에만 보관하고 Moti 서버에는 보내지 않습니다. Electron 메인 프로세스에서 OS 보안 저장과 AI 호출을 담당하며, 화면에는 키 등록·삭제·총평 요청 등 제한된 IPC만 노출합니다. 등록 시 입력은 전달하되 이후 키 원문 조회 기능은 노출하지 않습니다.
- 평문 설정 파일·브라우저 저장소·로그·오류 보고에 키를 남기지 않습니다. 보안 저장을 사용할 수 없으면 평문 저장으로 자동 전환하지 않습니다.
- 제공자별 허용된 HTTPS 주소로만 키를 보내고, 임의 주소나 리디렉션에 키가 전달되지 않도록 검증합니다. 화면 격리와 IPC 호출자·입력 검증도 함께 점검합니다.
- 별도 API 사용료, 전송 데이터, 사용량 확인 방법, 키 삭제·교체와 제공자 측 폐기 방법을 안내합니다. 앱에서 키를 삭제하는 것과 제공자에서 키를 폐기하는 것은 구분합니다.
- 별도 키와 제공자가 지원하는 최소 권한·사용 한도를 권장합니다. 기기가 감염되거나 같은 사용자 권한의 악성 코드가 실행되는 상황까지 완전히 보호한다고 주장하지 않습니다.

Windows의 Electron `safeStorage`는 DPAPI 기반 보호를 제공하지만 같은 사용자 권한으로 실행되는 다른 앱으로부터의 완전한 격리를 보장하지 않습니다. 실제 구현에서는 프로젝트에 고정된 Electron 버전의 지원 API를 확인합니다. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage), [Electron 보안 지침](https://www.electronjs.org/docs/latest/tutorial/security)
